# ibkr-cli

A Go command-line client for the **Interactive Brokers Client Portal
Web API 1.0 (CPAPI 1.0)** — modeled 1:1 on
[schwab-cli](https://github.com/rayli09/schwab-cli) and
[etrade-cli](https://github.com/rayli09/etrade-cli) (same layout,
conventions, and safety rails), with the endpoint surface taken from
the official IBKR Web API documentation and cross-checked against the
Python client [IBind](https://github.com/Voyz/ibind). Since
2026-10-24 the CLI is at **full functional parity with IBind**:
94 leaf commands covering all 85 IBind REST methods and all 8 of its
WebSocket subscription classes (see the parity table below).

IBKR publishes no official CLI, and CPAPI is the one IBKR API a CLI
fits: plain HTTPS + JSON against either a local gateway or IBKR's
direct OAuth endpoint. (The TWS API is a stateful socket protocol
meant for long-lived processes; it is deliberately not the route
here.) Full design: [docs/SPEC.md](docs/SPEC.md).

Two authentication modes sit behind one interface:

- **Mode G — gateway (default).** A local Client Portal Gateway holds
  the session; [IBeam](https://github.com/Voyz/ibeam) (Docker) owns
  login, 2FA, and session keepalive. The CLI never sees your IBKR
  password.
- **Mode O — OAuth 1.0a.** The CLI signs requests directly against
  `https://api.ibkr.com/v1/api`: live session token via a
  Diffie-Hellman exchange, HMAC-SHA256 per-request signing. The
  signing implementation is hand-written on the Go standard library
  and is a port of IBind's; tests verify it byte-for-byte against
  vectors generated by running IBind itself.

## Install

```sh
# With Go 1.27+
go install github.com/rayli09/ibkr-cli@latest

# Or build from source
git clone https://github.com/rayli09/ibkr-cli.git
cd ibkr-cli
go build -o ibkr-cli .
```

## Auth setup

```sh
ibkr-cli auth init        # interactive; writes ~/.config/ibkr-cli/config.json (0600)
ibkr-cli auth status      # two-tier session state
```

Config lookup: `--config` flag → `IBKR_CLI_CONFIG` → the default
path. The file must be mode 0600 (loading **refuses** a looser file —
it can hold OAuth token material). No credential is ever taken from a
command-line flag or printed by any command; `auth oauth-status`
reports presence and expiry only.

### Mode G — gateway via IBeam

1. Run the Client Portal Gateway under IBeam (IBeam's README has the
   maintained Docker setup). IBeam injects your credentials, handles
   2FA, and keeps the session alive with tickles. Default local
   endpoint: `https://localhost:5000/v1/api` (IBeam's port mapping).
2. `ibkr-cli auth init` → mode `gateway`, confirm the URL, optionally
   set a default account id.
3. `ibkr-cli auth status` — `authenticated` + `brokerage session`
   both true means you are fully live.

The gateway's certificate is self-signed; the CLI skips TLS
verification **only for loopback hosts** and never otherwise.

### Mode O — OAuth 1.0a (no gateway)

One-time onboarding in IBKR's self-service OAuth portal gives you a
consumer key, an access token, and an access token secret, plus two
RSA key pairs you generate (encryption and signature). You also
generate the Diffie-Hellman prime yourself, e.g.
`openssl dhparam -out dhparam.pem 2048`, and register it with IBKR.
`auth init` (mode `oauth`) collects: consumer key, access token,
access token secret, DH prime (hex), key paths, realm (default
`limited_poa`), and DH generator (default 2).

On first use the CLI performs the live-session-token exchange (RSA
decryption of the access-token secret → prepend; DH challenge; RSA-
SHA256-signed request) and caches the token — with its expiry — in
the 0600 config, so one-shot invocations do not repeat the exchange.
Order commands additionally open the brokerage session via
`/iserver/auth/ssodh/init`.

### The one-session gotcha

IBKR allows **one brokerage session per username across all
platforms**. A live session here and a TWS / IBKR website / mobile
login under the same username kick each other. Read-only endpoints
(portfolio, market data, contract search) work on the outer session;
orders require the brokerage session. The CLI models the two tiers
explicitly: order commands fail with exit code 3 and a clear message
when the brokerage session is not live, instead of sending into a
dead session.

Sessions idle out; the client tickles automatically before `/iserver`
calls that follow a quiet period, and `auth reauth` re-establishes
the brokerage tier (gateway mode: `POST /iserver/reauthenticate` —
beyond that, IBeam owns re-login and the CLI says so rather than
pretending).

## Agent quickstart (gateway mode)

The IBeam stack ships in this repo (`deploy/ibeam/` — compose file,
env template, runbook in `deploy/README.md`), and the `setup` command
drives it end to end. It is built for agents: **non-interactive**
(never prompts), **machine-readable** (`--json` verdict object), and
**self-diagnosing** (every failed step names its fix). It never reads
the IBKR password — compose reads `env.list` itself; setup only
reports which keys are set.

```sh
git clone https://github.com/rayli09/ibkr-cli.git && cd ibkr-cli
go build -o ibkr-cli .

cp deploy/ibeam/env.list.example deploy/ibeam/env.list
chmod 600 deploy/ibeam/env.list
$EDITOR deploy/ibeam/env.list   # IBEAM_ACCOUNT + IBEAM_PASSWORD (+ TOTP seed for unattended 2FA)

ibkr-cli setup --up --wait 180s --json
```

`setup` walks the stack in order — docker CLI → daemon → scaffold
dir → `env.list` (presence, 0600, required keys set, paper flag) →
container (`docker compose ps`, `--up`/`--down` to change it) →
gateway probe (`/iserver/auth/status`) → CLI config (report, or
`--init-config` to write a gateway-mode config non-interactively) →
two-tier session verdict — and prints one verdict object:

```json
{"ready": true, "stage": "paper-ready",
 "steps": [{"name": "docker-cli", "status": "ok", "detail": "…", "fix": ""}],
 "next_actions": ["ibkr-cli auth status", "…"]}
```

Stages: `paper-ready` / `ready` (exit **0**, only when the gateway is
authenticated **and** the brokerage session is live),
`stack-down` / `gateway-unreachable` / `session-not-authenticated`
(exit **3**), and `no-docker` / `bad-dir` / `no-env` (exit **2**).
The scaffold is paper-first (`IBEAM_USE_PAPER_ACCOUNT=true`); going
live means deliberately flipping that value in `env.list`.

Once `setup` reports ready, the smoke ladder:

```sh
ibkr-cli auth status       # two-tier session state
ibkr-cli accounts list     # accounts visible to the session
ibkr-cli market quote 265598   # AAPL — priming absorbed
ibkr-cli orders list       # live orders (none yet, on a fresh paper account)
```

Global flags: `--config`, `--base-url` (testing override), `--account`,
`--json`, `--timeout`. Exit codes are stable: **0** ok, **2** usage,
**3** auth/session, **4** API error (incl. rate limit), **5** an order
question is pending your answer.

### Snapshot priming

CPAPI market data is subscription-lazy: a first snapshot request for
a conid often returns nothing but the conid while the feed spins up.
`market quote` and `market chain` absorb this — they wait briefly and
re-request the unfilled conids once, then name any conid that stayed
empty (no subscription / market closed) on stderr instead of printing
a silent blank row.

### Option chains

CPAPI has **no chain endpoint**. `market chain` assembles one:
underlier conid (cached in a local conid cache) → strikes for the
expiry month → strike band around the last price (default ±15%) →
one `secdef/info` per strike×right to resolve conids for the exact
expiry date → batched snapshots with IV (field 7633), open interest
(7638), and Greeks (7308–7311). Legs whose snapshot carries no market
data are marked stale (`*`). This is more requests than a native
chain call would be — an accepted property of this API, not of the
CLI.

## Order safety: dry-run, whatif, and the question loop

`orders place`, `orders modify`, and `orders cancel` **send nothing**
without `--confirm`. Even the dry run is real work: it requires a live
brokerage session, runs the **whatif** preview
(`POST /iserver/account/{id}/orders/whatif`), and prints the ticket —
account id with its **PAPER** (DU…) / **LIVE** tag, side, quantity,
conid, price — plus the margin/commission impact, before any send
decision.

The same rail covers **every** mutation in the CLI, not just orders:
`auth logout`, `accounts switch` / `set-dynamic`, `orders suppress` /
`suppress-reset`, `portfolio invalidate-cache`, `watchlist create` /
`delete`, and the FA mutations (`fa model-save`, `invest-divest`,
`submit-transfers`, `preset-save`) all print their payload, stop at
DRY RUN without `--confirm`, and write to the audit log when sent.

```sh
# 1. Preview only (whatif; nothing sent)
ibkr-cli orders place --conid 265598 --side BUY --qty 10 --price 200

# 2. Place for real
ibkr-cli orders place --conid 265598 --side BUY --qty 10 --price 200 --confirm
```

**Questions are never auto-answered.** IBKR frequently answers a
placement with a confirmation question ("price exceeds…", "possible
margin deficit…"). When that happens the CLI prints the question
**verbatim**, exits **5**, and stops. You answer exactly one question
per invocation, explicitly:

```sh
ibkr-cli orders reply <reply-id> --confirm   # or --decline
```

A "yes" may raise the next question (another exit 5) or complete the
placement and print the order id. Every mutating call (and every
reply) is appended to a local 0600 audit log next to the config.

Paper vs live is an **account property** (DU… = paper), not a mode:
orders always name the account they target, and the ticket shows its
tag.

### Rate limits (enforced client-side, per route)

From IBKR's published Web API limits: snapshot 10 req/s; history max
5 concurrent; live orders / trades / partitioned P&L / portfolio
routes 1 req per 5 s; tickle 1 req/s; SSO validate 1 req/min;
scanner runs 1 req/s; scanner params and the /pa/* routes 1 req per
15 min. HTTP 429 is retried up to 3 attempts honoring `Retry-After`,
then surfaces as a typed rate-limit error (exit 4).

### Spec errata (found at build time, docs/SPEC.md §5 vs sources)

- `auth/status` is **POST**, not GET (official reference + IBind).
- The whatif path is `/iserver/account/{id}/orders/whatif`; the
  spec table's `order/whatif` does not exist.
- Snapshot option open interest is field **7638** (7633 is IV); the
  spec's candidate list had OI unresolved.
- The OAuth direct base URL `https://api.ibkr.com/v1/api` and the
  `oauth/live_session_token` exchange are confirmed by IBind's
  implementation and IBKR's OAuth docs; the signing port is verified
  against IBind-generated test vectors. It has not been exercised
  against a live IBKR account (none was available at build time).
- The spec's §5 tables enumerate 25 commands, not 21 as its headline
  said; all 25 were implemented in v1 (`auth init` and
  `auth oauth-status` included). The 2026-10-24 parity extension
  brings the total to 94.

### Not ported, honestly

- **OAuth-mode WebSocket handshake** — implemented exactly as IBind
  implements it (session cookie + `?oauth_token=`), and covered for
  gateway mode by a stub WS server in tests, but never exercised
  against a live IBKR account (none exists yet — same status as the
  P5 live smoke). If IBKR's production WS endpoint rejects the
  handshake, this is the first thing to re-check.
- **Flex Web Service and the Account Management API** — different
  products (reporting / account administration), not part of IBind;
  out of scope.
- **Full-universe contract enumeration** — CPAPI genuinely has no
  chain endpoint; see the chain note above.

## Development

```sh
go build ./...
go vet ./...
go test ./...
```

Tests never touch the real API. The OAuth 1.0a implementation is
checked against vectors produced by running IBind's own functions on
fixed inputs (DH challenge, base strings, RSA/HMAC signatures, live
session token derivation and validation). The command tree runs
end-to-end against an in-process stub CPAPI server covering: snapshot
priming (empty → filled), a placement raising **two** question rounds
before returning an order id, session expiry (exit 3), 429 retry and
exhaustion, the dry-run rail (stub proves nothing was placed), chain
assembly, and the 0600 config write. The parity extension adds stub
fixtures for every new endpoint group with E2E tests per group
(mutating commands proven dry-run-safe by stub call counters), a
stub WebSocket server exercising the stream commands' subscribe →
NDJSON → unsubscribe lifecycle, and byte-format tests for the WS
subscription payloads against IBind's formats.

CI (GitHub Actions) runs gofmt, vet, build, and tests on every push.
